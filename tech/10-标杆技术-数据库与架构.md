### 1.1 Redis 设计哲学
```
核心理念：
- 简单就是美（Simple is beautiful）
- 速度优先（Speed is a feature）
- 单线程模型（避免锁竞争）
- 内存存储（In-memory first）

设计决策：
1. 单线程模型
   - 避免上下文切换
   - 避免锁竞争
   - I/O 多路复用

2. 内存存储
   - 读写速度快
   - 数据结构简单高效

3. 持久化可选
   - RDB（快照）
   - AOF（追加）
   - 混合持久化
```

### 2.2 索引数据结构
```sql
-- B+ 树特性
-- 1. 非叶子节点只存索引
-- 2. 叶子节点存数据，双向链表连接
-- 3. 所有数据都在叶子节点

-- 聚簇索引 vs 非聚簇索引
-- 聚簇索引：数据和索引在一起，叶子节点存完整数据
-- 非聚簇索引：叶子节点存主键值（需要回表）

-- 覆盖索引
-- 查询字段都在索引中，不需要回表
CREATE INDEX idx_covering ON users(name, email, age);
SELECT name, email, age FROM users WHERE name = 'John';

-- 索引下推 (ICP)
-- MySQL 5.6+，在存储引擎层过滤数据
SELECT * FROM users WHERE name LIKE 'J%' AND age > 20;
-- 索引 (name, age) 可以在索引层过滤 age
```

### 2.3 事务实现
```sql
-- MVCC (多版本并发控制)
-- 每行数据有隐藏列：
-- DB_TRX_ID: 最后修改的事务ID
-- DB_ROLL_PTR: 回滚指针
-- DB_ROW_ID: 行ID

-- Read View
-- m_ids: 活跃事务ID列表
-- min_trx_id: 最小活跃事务ID
-- max_trx_id: 下一个分配的事务ID
-- creator_trx_id: 创建者事务ID

-- 可见性判断
-- 1. trx_id == creator_trx_id → 可见
-- 2. trx_id < min_trx_id → 可见
-- 3. trx_id >= max_trx_id → 不可见
-- 4. min_trx_id <= trx_id < max_trx_id → 判断是否在 m_ids 中

-- 隔离级别实现
-- READ UNCOMMITTED: 不加锁，不使用 MVCC
-- READ COMMITTED: 每次读创建新的 Read View
-- REPEATABLE READ: 事务开始时创建 Read View
-- SERIALIZABLE: 加锁
```

### 2.4 锁机制
```sql
-- 锁类型
-- 1. 表锁：锁整张表
-- 2. 行锁：锁单行数据
-- 3. 间隙锁 (Gap Lock)：锁索引间隙
-- 4. 临键锁 (Next-Key Lock)：行锁 + 间隙锁

-- 行锁模式
-- X 锁 (排他锁)：SELECT ... FOR UPDATE
-- S 锁 (共享锁)：SELECT ... LOCK IN SHARE MODE

-- 死锁检测
-- 等待图 (Wait-for Graph)
-- 检测到死锁后，回滚代价小的事务

-- 避免死锁
-- 1. 固定顺序访问表和行
-- 2. 保持事务短小
-- 3. 使用合适的索引
-- 4. 减少锁的范围
```

## 五、系统架构设计

### 5.1 CAP 定理
```
CAP:
- Consistency (一致性): 所有节点看到相同数据
- Availability (可用性): 每个请求都能得到响应
- Partition Tolerance (分区容错): 网络分区时系统仍能工作

分布式系统只能满足其中两个：
- CP: 放弃可用性 (如 ZooKeeper, etcd)
- AP: 放弃一致性 (如 Cassandra, DynamoDB)
- CA: 不存在 (单机系统)

实际选择：
- 大多数系统选择 AP + 最终一致性
- 金融系统选择 CP
- 缓存系统选择 AP
```

### 5.2 一致性模型
```
强一致性:
- 线性一致性 (Linearizability)
- 顺序一致性 (Sequential Consistency)

弱一致性:
- 最终一致性 (Eventual Consistency)
- 因果一致性 (Causal Consistency)

实现方式:
1. 主从复制 (强一致)
2. 多主复制 (最终一致)
3. 无主复制 (最终一致)
4. 共识算法 (Raft, Paxos)
```

### 5.3 Raft 共识算法
```
三种角色:
1. Leader: 处理所有写请求
2. Follower: 接收 Leader 复制的日志
3. Candidate: 参与选举

选举过程:
1. Follower 超时未收到心跳
2. 转为 Candidate，发起投票
3. 获得多数票成为 Leader
4. 定期发送心跳维持领导

日志复制:
1. Client 发送写请求到 Leader
2. Leader 追加到本地日志
3. Leader 复制日志到 Followers
4. 多数确认后提交
5. Leader 通知 Followers 提交
```

### 5.4 分布式存储架构
```
GFS/HDFS 架构:
┌─────────────────┐
│   Master Node   │ ← 元数据管理
└────────┬────────┘
         │
    ┌────┴────┐
    │         │
┌───┴───┐ ┌───┴───┐
│Chunk 1│ │Chunk 2│ ← 数据节点
└───────┘ └───────┘

数据分片策略:
1. 范围分片 (Range Partition)
2. 哈希分片 (Hash Partition)
3. 一致性哈希 (Consistent Hashing)

一致性哈希:
- 解决节点增减时数据迁移问题
- 虚拟节点保证负载均衡
```
